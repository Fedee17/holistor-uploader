# PATRONES TÉCNICOS APRENDIDOS EN PRODUCCIÓN

## n8n específico

- **Antes de diagnosticar un comportamiento raro, leer este archivo y `8_informe_pruebas_de_ruptura_2026-09-24.md`.** El 01/10/2026 se volvió a diagnosticar desde cero (dos corridas a la vez del mismo cliente) algo que ya estaba explicado y con solución propuesta desde el 24/09: ahorró tiempo leerlo, y se perdió tiempo por no haberlo hecho.

- Nodos Google Sheets v4.5: siempre requieren `resource: "sheet"` + `operation`. Sin estos campos el nodo falla silenciosamente al importar. **Excepción confirmada**: cuando el `operation` es el que viene por defecto para el `resource` elegido, n8n puede no guardarlo explícito en el JSON — no es un campo faltante real. No asumir que la ausencia del campo `operation` es un error sin antes confirmar cuál es el default real de ese `resource`.
- Nodos Google Drive v3: requieren `resource: "file"` + `operation`. Mismo matiz que arriba.
- HTTP Request con credenciales OAuth: para usar `predefinedCredentialType: "googleSheetsOAuth2Api"`, la credencial necesita "Allow use in HTTP Request node" activado — viene desactivado por defecto.
- **Expresiones de n8n llevan un solo `=` al principio, nunca dos.** Un campo armado como `=={{ ... }}` no es "más enfático" — el segundo `=` rompe el campo. Confirmarlo mirando el JSON crudo del nodo.
- **Comparar un valor booleano contra un booleano usando el tipo "String" en un nodo IF, con `typeValidation: strict`, corta la ejecución en seco.** Error real: `"Wrong type: 'true' is a boolean but was expecting a string"`. Fix: cuando la expresión de la izquierda ya da un booleano real, el selector de tipo de la condición tiene que estar en **Boolean**, no en String — lo más limpio es el operador booleano de valor único ("is true").
- `$getWorkflowStaticData('global')` no es thread-safe entre ejecuciones paralelas. Usar scoping por key compuesta. Siempre re-asignar el objeto: `sd.procesos[key] = p` al final para forzar persistencia.
- `responseMode: responseNode`: el webhook espera hasta que el nodo `respondToWebhook` ejecuta. Un nodo sin `continueOnFail: true` que falla corta la cadena → el webhook nunca responde → el frontend hace timeout.
- `continueOnFail` debe estar activo en: nodos de Drive, Sheets, Gemini, cualquier nodo que pueda fallar en producción (incluyendo errores transitorios de sobrecarga de la API, no solo bugs de datos). En la práctica esto puede requerir activarlo manualmente por nodo desde la UI de n8n. Auditado el 16/09/2026 sobre los 130 nodos: el único que faltaba era `Actualizar Huella Factura` (corregido con `onError: continueRegularOutput`).
- ⚠️ **`continueOnFail` evita que el bucle se corte, pero NO protege el conteo de completitud si el crash ocurre en un nodo que participa de ese conteo.** Caso real: una variable sin declarar (`cuitClienteArchivo`, usada como respaldo sin el mismo chequeo `typeof` que su variable hermana) causó un `ReferenceError` dentro de `Generar PRN`, para una sola factura de un lote de 18. El bucle no se cortó, pero el crash rompió el conteo de completitud (`_terminales` vs `_esperados`), y `Armar PRN Final` nunca corrió. Ante un "no se generó ningún PRN" con facturas que sí deberían haber andado, revisar primero si hubo un error sin capturar en algún punto del bucle. Fix general: cualquier variable usada como respaldo de otra debe tener el mismo chequeo de existencia (`typeof x !== 'undefined'`) que la variable principal.
- `alwaysOutputData` necesario en nodos de filtro — si devuelven 0 items, los nodos siguientes no ejecutan y el proceso queda colgado. Caso real: `Buscar_archivos` no lo tenía, y con la carpeta de Entrada vacía el proceso quedaba colgado sin avisar; ya está activado (verificado en la versión `6d023a65`).
- Zombie timeout: máximo recomendado 15 minutos para 200+ facturas. `executionTimeout` del workflow: 2400 s, es el máximo de la instancia (no se puede subir a 3600). A ~28 s por factura nueva, ~80 facturas por corrida; la página parte en tandas de 40.
- **Estado de proceso — read-and-reset**: `Preparar Respuesta Estado` devuelve `listo: true` UNA SOLA VEZ y resetea `proceso_listo = false` en el mismo momento. Nunca comparar timestamps para distinguir corridas.
- **SplitInBatches typeVersion 3 — comportamiento crítico**: la salida `out0` (Done) se dispara después de CADA loop-back, no solo al terminar todos los batches. Fix con guardas: verificar con un contador (`hechos >= total`) que el procesamiento esté completo antes de actuar. Usado en `Finalizar PRN Unico`, el loop de `Actualizar Estado Facturas`, y el de `Resolucion FALLOS`. La arquitectura padre-hijo elimina este problema de raíz.
- `continueOnFail` — formato del error en el item resultante: es un OBJETO `{name, message}`, no un booleano. Un IF con `typeValidation: "loose"` trata ese objeto como truthy. Siempre usar `$json.error === true` (estricto).
- **`!campo` como señal de fallo es una trampa cuando un camino legítimo manda ese campo vacío a propósito.** Caso real: `Acumular PRN` usaba `!j.prn_content` para detectar fallos, y el escaneo manda `prn_content: ''` porque no genera línea; las facturas nuevas caían como "fallida / carga manual". Fix: caso explícito por tipo (`es_nueva_escaneo === true`) antes del chequeo genérico.
- **`sd[lmKey]` — acumulador top-level confiable**: patrón para acumular datos por corrida cuando `sd.procesos[key]` no persiste confiablemente entre llamadas del Bucle. Fix obligatorio en `Resetear Estado`: `sd['lm' + processKey] = {};` antes del return.
- **`appendOrUpdate`/`update` con `matchingColumns` de texto NO es confiable en una hoja con cientos de filas.** El nodo puede terminar escribiendo sobre la fila 2 en vez de la fila real, sin reportar error. Fix real: identificar la fila por su número físico (`row_number`), no por coincidencia de valores.
  - `row_number` no se agrega automáticamente de forma confiable en la lectura de Google Sheets en n8n. Calcularlo manualmente: `row_number = índice_del_array + 2` (la fila 1 es siempre el encabezado). Calcular esto ANTES de aplicar cualquier filtro que salte items.
  - Con `row_number` disponible, usar `operation: 'update'` + `matchingColumns: ['row_number']` (no `appendOrUpdate`).
  - **Cuando un nodo nuevo se encadena justo después de un nodo que llama a una API, y necesita datos que ese nodo tenía en su ENTRADA (no en su salida), no asumir que esos datos siguen disponibles vía `$json`.** La salida de un nodo que llama a una API se reemplaza por la respuesta de esa API. Buscar esos datos en un nodo MÁS ATRÁS en la cadena. Caso real: `Actualizar Huella Factura`, encadenado después de `Actualizar Estado Facturas`, fallaba porque leía de `$json` en vez de `$('Loop Actualizar Estado').item.json`.
  - Patrón extendido a FALLOS: `Append FALLOS`/`Append FALLO HOT` bifurcan por IF según si el ítem trae `row_number` — con `row_number`, `update` (HTTP PUT); sin él, `append` puro.
- **Todo append a Sheets con `cellFormat: RAW`.** Con `USER_ENTERED` Google interpreta lo que recibe: un total como `7311.02` se guardó como fecha (48 filas reales), un CUIT puede pasar a notación científica, y una fórmula en el Excel de ARCA se ejecutaría en la hoja. Aplicado el 16/09 en los seis nodos de append.
- **Un campo que la página manda tiene que estar declarado en CADA nodo intermedio hasta la hoja.** Caso real (H-12): la página mandaba el desglose de ARCA desde hacía tiempo, pero `Comparar Registro` y `Preparar Filas Nuevas` reconstruyen cada fila con una lista fija de campos (`normRow`) y `Insertar Registro Nuevo` escribe solo las columnas mapeadas — el campo se perdía en silencio y la columna de la hoja quedó vacía en 2.155 filas sin que nadie lo notara. Al agregar un campo nuevo, seguirlo nodo por nodo hasta la celda.
- **Marcar un estado final en la hoja solo cuando el resultado que ese estado promete existe de verdad.** Caso real (H-01/H-02, 16/09): 23 facturas quedaron `procesada` en REGISTRO_ESPERADO aunque el PRN nunca se guardó, y desde entonces eran invisibles para el sistema. Fix: `Preparar Actualizacion Estado` exige `p.prn_guardado === true`.
- **`REGISTRO_ESPERADO` es solo-append (sin update por rate limit).** Recargar un Excel para un período ya cargado inserta filas nuevas (con la firma nueva) y deja las viejas: la hoja acumula duplicados por clave. `Indexar Registro` los colapsa en una sola vista (procesada > fallida > pendiente) y desde 17/09/2026 conserva el `desglose_arca` entre duplicados de la misma clave. Decisión del estudio (17/09): se aceptan los duplicados; actualizar en el lugar queda para más adelante.
- **Importar un JSON de workflow sobre un workflow existente en n8n hace MERGE, no reemplazo, si el lienzo no está vacío antes de importar.** Antes de importar un JSON actualizado: seleccionar todo el lienzo (Ctrl+A) y borrarlo (Delete) primero.
- **Cambios manuales en la UI de n8n pueden pisar cambios aplicados antes por API**, y viceversa. Regla práctica: después de cualquier sesión donde ambos lados tocan el mismo workflow, releer el nodo específico antes de asumir que un fix anterior sigue en pie. Caso real: el fix "no reconvertir USD si ya coincide con ARCA" figuraba como resuelto en la documentación y no estaba en el código desplegado; hubo que reaplicarlo el 16/09.
- **Renombrar un nodo en n8n rompe silenciosamente todas las referencias `$('NombreDeNodo')`** que otros nodos usan para leer sus datos.
- **Errores transitorios de sobrecarga de la API de Gemini** también requieren `continueOnFail` en los nodos que la llaman.
- **`get_workflow_details` puede devolver la versión PUBLICADA, no el borrador más reciente.** Confirmar si hace falta publicar el cambio.
- **`get_workflow_execution` de una corrida grande (131 nodos, 40 facturas) pesa más de 1 MB**: siempre pedirla con `includeData` y `truncateData: 1`, dejar que la herramienta la guarde en archivo y buscar adentro con Python (`json.load` + `re.finditer`), en vez de intentar leerla entera. Así se encontró en segundos el `total_extraido` de VETAGRO entre 60 nodos.
- **`setNodeParameter` puede reportar éxito sin persistir realmente el cambio** (comportamiento intermitente observado varias veces). Cuando esto pasa, `updateNodeParameters` con `replace: true` funciona de forma más consistente — usarlo directamente en vez de reintentar `setNodeParameter`. Verificación que siempre funciona: volver a bajar el workflow y comparar el `jsCode` byte a byte con el archivo local (hecho el 17/09/2026: los cinco nodos quedaron idénticos).
- **Cuando `get_workflow_execution` muestra `status: "running"` durante mucho tiempo, no es necesariamente que siga corriendo genuinamente** — puede ser el mismo problema de la API de monitoreo que no refleja progreso en vivo. Volver a consultar más tarde suele mostrar `status: "success"` una vez que efectivamente terminó.
- **La memoria del workflow (`$getWorkflowStaticData`) NO es compartida en vivo entre ejecuciones en n8n Cloud (probado 24/09/2026 en PRUEBA).** Cada ejecución arranca con una copia de lo guardado, trabaja sobre su copia y al terminar guarda la copia ENTERA encima de lo que haya (gana el último que termina). Evidencia: ejecuciones 29622/29623 (mismo cliente, 1 s de diferencia: la segunda no vio `procesando:true` de la primera y cerró el proceso mientras la primera seguía con Gemini) y corridas A/B de clientes distintos (al terminar A desapareció el proceso de B). Consecuencias: el freno de 8 s y el chequeo `procesando === true` de `Resetear Estado` solo detectan corridas colgadas de antes, nunca una en curso; dos clientes a la vez se pisan; `Estado` no ve el avance real (devuelve el resultado anterior con `desde_cache:true` hasta que la corrida termina); el `_dirty_tick` no cambia nada de esto. Lo que va a la planilla (PRN_LINEAS, REGISTRO_ESPERADO) sí persiste. Fix de fondo pendiente: estado de corrida en una pestaña PROCESOS o en una Data Table de n8n. Ver `8_informe_pruebas_de_ruptura_2026-09-24.md`.
- **Recargar un Excel de ARCA sin filas nuevas agrega una fila vacía a REGISTRO_ESPERADO** (solo `periodo` y `cliente_cuit`): `Preparar Filas Nuevas` emite un ítem marcador `_no_registro_rows` que entra igual a `Insertar Registro Nuevo`. Es el origen de las filas 2520–2521 y 3032–3033 de Castellano en producción. Fix chico pendiente.
- **`Webhook Upload` sube a Drive lo que llegue**: sin CUIT (`sincuit__…`), archivos que no son PDF, `.txt`. La corrida los marca fallidos sin romperse, pero quedan en Entrada y se vuelven a mandar a Gemini en cada corrida del cliente. Con Entrada vacía, el ítem vacío de `Buscar_archivos`/`Filtrar Por Cliente` (alwaysOutputData) entra al bucle: 4 reintentos de descarga (55 s) y `archivos_estado: {desconocido: fallida}`.
- **Un reinicio del servidor de n8n Cloud puede dejar el flujo SIN PUBLICAR, y nadie se entera.** Caso real (22/09/2026, dos veces: 08:21 y 09:16 ART): una tanda de ejecuciones queda marcada `crashed` con el mismo `stoppedAt` (así marca n8n lo que estaba en curso cuando el proceso se reinició), y después del reinicio el flujo aparece `active: false` / `activeVersionId: null`, sin que cambie `updatedAt`. Desde afuera se ve como `Failed to fetch` en la página (la respuesta 404 llega sin encabezados CORS). No hay ninguna otra ejecución registrada en el medio: las órdenes no llegan a n8n, así que nada queda a medias. Solución operativa: el vigilante (`il3NDjTi8CA4UD9s`). La causa del reinicio NO está confirmada: coincidió dos veces con una tanda de verificaciones en paralelo al arrastrar PDF, pero la misma tanda (65 simultáneas) sobre la misma instancia en el ambiente de prueba no tiró nada. n8n Cloud no expone memoria ni logs; solo el soporte puede decirlo.
- **Verificación al arrastrar PDF: una llamada con todas las firmas, no una por archivo (22/09).** Antes, `Promise.all` disparaba 65 llamadas a `holistor-verificar` y cada una leía REGISTRO_ESPERADO entera. Ahora `Chequear Huella` recibe `huellas: [...]`, la planilla se lee una vez y se resuelve todo contra un índice firma → fila. La página cae al modo anterior (de a `VERIFICACION_CONCURRENCIA = 3`) si la respuesta no trae `resultados`. Mejora de eficiencia comprobada; no es una cura confirmada de los reinicios.
- **Gemini lee el signo negativo impreso en una nota de crédito.** `total: "-29.780,44"` en la NC VETAGRO (22/09). La línea PRN salía bien (positiva, como ARCA), pero `Armar PRN Final` comparaba `29780.44` contra `-29780.44` y la mandaba a "total a revisar". Desde el 22/09 la conciliación compara en valor absoluto. Regla: cualquier comparación de importes entre Gemini y ARCA tiene que ser tolerante al signo, porque ARCA guarda las NC en positivo y el signo lo da el tipo de comprobante.
- **La herramienta `updateNodeParameters` des-escapa `\uXXXX` dentro del `jsCode`.** Al mandar `/[\u0300-\u036f]/` el nodo quedó con los caracteres literales U+0300–U+036F dentro del corchete. En una clase de caracteres de una regex es equivalente (verificado con `node`), pero conviene saberlo: un `\u` que sí tenga que quedar como texto (por ejemplo dentro de un string que se compara) puede cambiar de significado. Revisar el nodo bajado después de cada envío.
- **Duplicar un workflow desde la UI de n8n regenera el `webhookId` interno de cada webhook pero copia el `path` tal cual.** Dos workflows publicados con el mismo `path` + método no pueden convivir: `publish_workflow` falla con "There is a conflict with one of the webhooks". Al duplicar para un ambiente de prueba hay que renombrar los diez `path` (sufijo `-test`) y revisar que no choquen con otros workflows viejos (pasó con `holistor-procesar-test`, que ya usaba el prototipo padre-hijo).
- **Tope de tiempo de ejecución en n8n Cloud plan Pro: no está publicado.** El foro mezcla "40 minutos" (hilo viejo), "sin límite" (mayo 2026) y un empleado de n8n que dice que el valor por plan solo lo da help@n8n.io por escrito. Dato firme de esta instancia: el 16/09 no dejó pasar de 2400 s. Hasta tener respuesta escrita, el tamaño de tanda sigue en 40.
- **Banco de pruebas local del código real.** El código de `Generar PRN` se puede correr fuera de n8n con `new Function('$','$input','$getWorkflowStaticData','require', code)` y datos reales de una ejecución. Es la forma de probar un cambio en 30 segundos sin gastar Gemini ni tocar las hojas, y de simular una corrida entera (23 facturas reales con la salida real de Gemini) antes de publicar. Una simulación que pasa no reemplaza la corrida real: confirma la lógica, no el comportamiento de n8n.
- **`updateNodeParameters` con `replace: true` reemplaza el objeto ENTERO de parámetros del nodo: lo que no se manda se pierde.** Caso 16/09/2026: al restaurar `Analyze document` se mandaron solo `resource`, `modelId` y `text`, sin `inputType: binary`. En la corrida siguiente (ejecución `25894`) Gemini contestó "No se proporcionó ningún documento" o completó el JSON con los ejemplos del propio prompt (CUIT de ejemplo, "EMPRESA TEST SA", el EJEMPLO 4 de YPF palabra por palabra); con `inputType: binary` agregado, la ejecución `26163` leyó bien las 23 facturas. Regla: antes de reemplazar parámetros, bajar el nodo hermano que funciona (`Analyze document Ligero`) y copiar su estructura; después de publicar, volver a bajar y comparar clave por clave. Si el nodo trae un campo largo (el prompt), guardar una copia local antes: el campo puede perderse del todo.
- **Guardar por API deja un BORRADOR; no está en producción hasta publicar.** Después de cada cambio comparar `versionId` con `activeVersionId` (y, ante la duda, `get_workflow_history`). Casos: el arreglo de `Acumular PRN` estaba guardado pero sin publicar (16/09); el flujo entero apagado dos veces (16/09 y 18/09). Un `404 ... is not registered` en un webhook es flujo apagado; un `403` es flujo encendido sin el encabezado.
- **Hay más de una sesión con acceso a los flujos** (este chat, otros chats, Claude Code); en el historial de versiones todas figuran igual ("Federico (via MCP)") y no se pueden distinguir por el autor. El 01/10 aparecieron tres publicaciones (arreglo de dólares, su corrección y el port del candado) entre dos intervenciones de este chat. Antes de editar: leer el historial; después de editar: poner nombre y descripción a la versión.
- **Candado compartido en Sheets (01/10/2026)**: para saber si una corrida está viva no sirve nada que viva en `staticData` (se graba al terminar). Se lee una hoja en tiempo real antes de decidir (`Leer PROCESOS_ACTIVOS` → `Resetear Estado`). Decisiones de diseño: (a) **falla hacia el lado de dejar trabajar** — los nodos de Sheets reintentan 3 veces y siguen aunque fallen, y si la lectura no trae filas no se bloquea; (b) **la misma regla está en dos nodos** (`Resetear Estado` y `Evaluar Candado`), al cambiar una cambiar la otra; (c) al leer una hoja que puede venir vacía, el nodo necesita `alwaysOutputData`, y el Code que la consume debe filtrar los ítems sin `process_key`; (d) `Resetear Estado` toma el cuerpo del pedido de `$('Webhook Procesar')` porque su entrada pasó a ser la hoja. No cubre dos clientes distintos a la vez (ver `2_workflow_estado.md`).

## Gemini en n8n — inconsistencias conocidas de extracción (siempre validar en el código)

- **No asumir que Gemini es la causa de un bug sin contarlo contra la evidencia real.** La mayoría de los bugs reales de este proyecto son del propio código — las rarezas de extracción de Gemini son una categoría real pero minoritaria. Dicho esto, Gemini SÍ tiene no-determinismo real y confirmado: la misma factura, reprocesada en corridas distintas, puede devolver campos vacíos en una corrida y con valor `"0"` en otra, o leer un dato clave (como el CUIT del receptor) de forma distinta entre corridas. Caso medido (FRANK NADIA 2026-08, tres corridas sobre los mismos 23 PDF): 4 mal en la primera, 3 en la segunda, 2 en la tercera — nunca las mismas.
- **Las reglas de autoverificación escritas en el prompt no son un control.** El prompt de `Analyze document` ya dice de dónde sale `neto_gravado`, que "Subtotal Exento" es EXC, y pide comprobar que los importes sumen el total (Regla 6) — y Gemini igual devolvió neto+IVA+percepción = 3.356.836 contra un total de 3.068.007 sin corregirse. Lo que garantiza el resultado es el control determinístico en `Generar PRN`, no el pedido en el prompt.
- **Gravado ↔ exento invertidos (Monroe Americana, 4 de 12 facturas en una corrida).** Pie con "Subtotal Exento" y "Subtotal Gravado" en renglones consecutivos: Gemini a veces asocia cada etiqueta con el número del renglón de al lado (neto = exento y viceversa), a veces inventa el IVA como 21 % del exento, y a veces pone el exento con código NGC. Detección: IVA ≠ neto × alícuota, o IVA = alícuota × el monto exento. Fix definitivo: cruce contra el desglose de ARCA (abajo). Confirmado en producción el 17/09 (ejecución 26562): dos facturas invertidas de nuevo, las dos corregidas solas.
- **Cruce de importes contra el desglose de ARCA (desde 17/09/2026, `Generar PRN`).** Si la factura matcheó una fila de `REGISTRO_ESPERADO` con `desglose_alicuotas`, la fila cierra contra su propio total (±1 peso) y la factura está en pesos, se compara neto e IVA por alícuota (±5 pesos, porque ARCA deriva el neto desde el IVA y difiere del PDF en centavos), exento (EXC), no gravado (NGC) y total; ante diferencia se toman los valores de ARCA y queda `Corregido con desglose ARCA (...)` en `advertencias`. Si los montos de EXC/NGC coinciden pero el código está cambiado, solo se recodifica. Las percepciones no se corrigen (ARCA solo trae la suma "Otros Tributos", sin código): si no coinciden queda un `Aviso desglose ARCA`. Conceptos que Gemini clasifica como NGC y ARCA cuenta en "Otros Tributos" (impuestos internos) se respetan. Sin desglose (filas viejas, facturas B/C, USD) no se cruza nada.
- **Alícuota: nunca recalcularla desde IVA/neto y redondear a la válida más cercana.** Esa regla existió hasta el 17/09/2026 e inventó alícuotas de 2,5 % y 0 % sobre facturas al 21 % con gravado/exento invertidos. Ahora: si IVA/neto da exactamente una alícuota válida (±0,1 punto) y difiere de la etiquetada, se corrige la etiqueta (neto e IVA impresos, aritmética exacta); si no da ninguna, la factura sale fallida con motivo `IVA no coincide con neto × alícuota`. Antes de diagnosticar "alícuota inventada", verificar dos veces: un error de columna al leer el Excel de ARCA puede parecer el mismo síntoma sin serlo.
- **Control final de suma (desde 17/09/2026).** Antes de armar la línea: neto + IVA + IVA adicional + NG/EX + percepciones tiene que dar el total (±2 pesos o 0,5 %). Si no, fallida con motivo detallado. Excepción exacta: si los componentes no cierran contra el total que leyó Gemini pero sí contra el total de ARCA, el error es la lectura del total y se toma el de ARCA (aviso `Total corregido con ARCA`).
- **Corrección "por total de ARCA" (la vieja, anterior al cruce por alícuota) solo vale para facturas de un único componente.** Recalcular neto e IVA desde el total ignorando exento, percepciones y segunda alícuota inventaba un neto gravado en facturas con exento (caso real: neto 28.672 → 319.389) y con `alic: "0"` tomaba 21 %. Desde el 16/09 se aplica solo si `conceptos_ngex`, `retenciones` e `iva_adicional` están vacíos y `alic > 0`.
- **Confusión emisor ↔ receptor**: el campo "Nombre:"/"Cliente:" del cuerpo es el receptor, no el emisor; el CUIT del encabezado es del emisor.
- **CÓDIGO IVA vs cpbte AFIP**: el recuadro "CÓDIGO 01" es la categoría de IVA del emisor (RI=01), NO el código de comprobante AFIP.
- **Formato de números mixto**: Gemini devuelve importes en distintos formatos en la misma sesión. `fmtNum` debe detectar el formato analizando posiciones y largo de grupos, nunca asumir uno solo.
- **N/A en campos numéricos**: a veces devuelve "N/A". `fmtNum` debe convertirlo a `""`.
- **Códigos AFIP inválidos o inconsistentes con la letra**: marcar como fallido con motivo explícito, nunca auto-corregir.
- **Código de barras como CUIT**: en algunos PDFs Gemini extrae el código de barras (40+ dígitos) en vez del CUIT. Regla en prompt: CUIT son exactamente 11 dígitos numéricos.
- **CUIT con un dígito cambiado**: Gemini leyó `30517050095` por `30517059095` (Monroe). El enriquecimiento por número + tipo + total contra `REGISTRO_ESPERADO` lo corrige; sin ARCA cargado, el dígito verificador lo frena como fallida.
- **`numero_hasta` vacío**: el prompt de reintento entrega `"numero_hasta": ""` como plantilla. Toda clave (idempotencia, dedup, conciliación) tiene que usar `numero_hasta || numero_desde` con una sola función; hasta el 16/09 una de las cuatro claves usaba `0` y descartaba la segunda factura del mismo proveedor y punto de venta como "mismo lote".
- **Retenciones/conceptos con monto=0**: filtrar antes de escribir al PRN.
- **COSENO FI y similares (ajustes negativos dentro del neto)**: no son NG/EX — el código descarta conceptos con valor negativo automáticamente.
- **Cantidad extraída como neto_gravado**: en facturas con layout de tabla, Gemini puede extraer la cantidad de unidades como neto_gravado. Validar ratio IVA/Neto ≤ 50%; si supera ese umbral, marcar fallida.
- **Percepciones alucinadas**: si una columna del pie está vacía, Gemini a veces extrae un número cercano igual. El código descarta percepciones si Neto+IVA+iva_adicional+NG/EX ya explica el Total (dentro de $2 de tolerancia).
- **Filtro de "IVA confundido con NG/EX o percepción" — usar el IVA REAL, no `total-neto`.** Falla en facturas 100% exentas (`neto=0`). Usar `d.iva_liquidado` real cuando está disponible y es > 0; solo aproximar con `total-neto` cuando hay neto gravado > 0.
- **Multi-alícuota: el neto de la línea principal debe ser el neto ESPECÍFICO de esa alícuota**, no el "Neto Gravado" combinado. Cuando hay `iva_adicional` y el neto de la línea principal no es coherente con su propio IVA (tolerancia ~2%), derivar el neto correcto como `iva_liquidado / (alícuota/100)`.
- **Notas de Débito / facturas con recuadro-resumen al pie**: el cuerpo puede mostrar todo en cero mientras el monto real está SOLO en una celda del recuadro resumen del pie. Revisar siempre las 6 celdas del recuadro.
- **Comprobantes tipo C de Monotributista con neto/IVA en cero (no vacío)**: Gemini a veces devuelve ceros explícitos en vez de dejar los campos vacíos en facturas C genuinas. Fix: si es tipo C y todo viene en cero con total positivo, usar el total como neto igual.
- **Variantes de puntuación en percepciones**: "Percepción IVA" / "Perc. IVA" / "P.I. IVA" / "Perc. I.V.A." → todas mapean a `PI01`.
- **`fmtNum` con dos o más puntos, donde el último grupo NO tiene 3 dígitos** (ej. `"8.805.62"`): con 2+ puntos, los grupos anteriores al último siempre son de miles; si el último grupo tiene menos de 3 dígitos, se trata como decimal.
- **Campo `moneda` de ARCA no es confiable para decidir si una factura está en pesos o dólares**: ARCA exporta `moneda='$'` en ambos casos. Fix: ignorar ese campo y usar solo `tipo_cambio > 1` como criterio.
- **`iva_adicional` puede volver como objeto en vez de array** cuando hay exactamente un elemento adicional. Fix: normalizar siempre con un `toArray()` que envuelva el objeto en lista (`[v]`), no que devuelva `Object.values(v)` — esa versión perdía la segunda alícuota sin aviso hasta el 16/09.
- **Recuperación de `pdf_nombre` si `Generar PRN` crashea**: el ítem de error puede no traer `pdf_nombre`, lo que bloquea `Finalizar PRN Unico` para TODAS las facturas del lote. Fix defensivo en `Acumular PRN`: recuperar el nombre desde `Edit Fields` o `Download file` como fallback.
- **`Reenganchar Binario para Reintento`**: `Analyze document` no conserva el binario del PDF en su salida. Cuando el JSON no es válido y hace falta reintentar, el nodo necesita el binario de nuevo. Fix: `binary: $('Download file').item.binary` reenganchado antes del segundo intento. **El mismo problema aplica a cualquier nodo Gemini nuevo** — ver diseño de duplicados más abajo, donde `Calcular Clave Temprana` hace exactamente este reenganche antes de dejar pasar una factura a la lectura completa.
- **La lectura liviana (`Analyze document Ligero`) lee mal el punto de venta**: medido el 16/09, acertó la clave en 1 de 23 facturas, así que en la práctica no evita ninguna lectura completa y cuesta 4 s por factura. Opciones pendientes: pedir el punto de venta tal como aparece en `Nro: 0003106-00004625`, extraerlo del nombre del archivo antes de llamar a Gemini, o desactivarla hasta medir >80 % de aciertos.
- Facturas Toolking (maquinaria): IVA 10,5%, neto en columna "P. Base". `cod_neto = CBU`.
- Facturas La Pastora del Norte (harina): IVA 10,5%, totales >$17M → overflow posible. Validar con `fmtNum(v, maxWidth=11)`.
- Centro de Embalajes — "Costo Financiero a descontar": ítem negativo, no es NG/EX.
- Parque Industrial Piloto de San Francisco — facturas de energía (múltiple alícuota): NETO I.V.A. 27% + FDO.INF.OBRA E.E.P.I. 21% → línea extra PRN. COSENO FI: NO va en conceptos_ngex. `cod_ngex_override="EXC"` en PROVEEDORES.
- Monroe Americana (droguería, FRANK NADIA): facturas mixtas con "Subtotal Exento" grande y "Subtotal Gravado" chico al 21 %, más Perc. IVA RG 3337 al 3 % (`PI01`). Es el proveedor donde se detectó la inversión gravado/exento.
- **Cuando Gemini no recibe el documento no falla: inventa.** Devuelve JSON válido armado con los ejemplos del prompt o dice "No se proporcionó ningún documento". Señales: CUIT o razón social de los ejemplos, la misma fecha en facturas distintas, importes redondos, o los números del EJEMPLO 4 de YPF. Lo atajaron los controles de suma de `Generar PRN` (las facturas fueron a carga manual en vez de salir al PRN), pero no hay que confiar solo en eso.
- **`Service unavailable - try again later` es una caída pasajera de Google, no un problema de la factura** (01/10/2026: tres veces en ~2 minutos). Los reintentos cortos (3 × 1 s) no la cubren. Reintentar con espera (5 × 5 s es el máximo que permite n8n entre intentos) y distinguirla de "Gemini no devolvió texto válido" con un tipo propio (`gemini_no_disponible`), porque el primero se arregla con "Reintentar fallidas" y el segundo con carga manual. Desde el 07/10 está en producción (versión `f8afe5e3`), pero todavía no se probó ante una caída real de Gemini.
- **El rubro (`cod_neto`) que devuelve Gemini es inestable por proveedor**: la misma factura de BAUCLA salió SER, GB o CGG según la corrida. Para un proveedor conocido usar `forzar_rubro = SI` en PROVEEDORES; el prompt solo orienta. Un código nuevo (`GF`) hay que agregarlo en el prompt **y** cargarlo en PROVEEDORES con `forzar_rubro`, y confirmar que exista como Tipo de Movimiento en Holistor.
- **Facturas de flete de granos** (CTG/CPE, toneladas, descripción con el nombre del grano, sin la palabra "flete"): Gemini las clasifica como compra de granos (`CMG`). La señal que las distingue es el precio por tonelada (menor a $60.000). Regla en el prompt desde el 30/09 + `forzar_rubro` para los fleteros conocidos.
- **Los ejemplos del prompt se filtran a la respuesta cuando el modelo duda.** Al agregar un ejemplo con datos concretos, usar CUITs y montos que no puedan confundirse con los de una factura real, y recordar que cada ejemplo agregado también alarga el prompt (27.857 caracteres hoy).

- Los archivos se prefijan con CUIT para evitar mezcla entre clientes.

- **`Download file` con el ID pegado a mano puede terminar con un ID de credencial en vez de la expresión correcta**. Verificar siempre que los campos de ID de archivo usen una expresión dinámica.
- **Tercer y cuarto caso del 403 pasajero (22/09/2026, SUC. DE CASTELLANO en producción): 2 subidas rechazadas 3 veces cada una dentro de una ventana de 18 s (ejecuciones 28608–28614, 0,35 s cada una; la subida anterior y la siguiente, con la misma credencial y carpeta, anduvieron), y 2 movidos rechazados (uno por tanda).** Consecuencia real del movido fallido: el PDF queda en Entrada, la tanda siguiente lo vuelve a encontrar y, si se elige "Reprocesar todas", la factura sale dos veces en el consolidado. Siempre volver a bajar el workflow después de publicar y comparar contra el respaldo: la versión activa puede no ser la que uno creyó publicar.
- **El error 403 transitorio de la API de Google no es exclusivo de las subidas — también puede aparecer al mover un archivo (`Move file`)**, mismo origen (límite de velocidad bajo muchos pedidos seguidos). Detalle real observado: aunque el nodo devolvió el error, el archivo terminó apareciendo igual en Procesados — posible que el pedido haya funcionado del lado del servidor pero la respuesta llegara con error. Hasta el 22/09/2026 el sistema no reintentaba el movido (`Verif Move` solo detecta el error y deja un aviso en `advertencias`); desde esa fecha `Move file` reintenta solo (5 intentos, 5 s) antes de dar el error, y `Verif Move` sigue igual para el caso en que se agoten. Segundo caso real (16/09/2026): "Forbidden" al mover `FC-3106-00004625.pdf`; el archivo quedó en Entrada y la factura se procesó igual. En la corrida del 17/09 no hubo errores de movido.

Sí puede copiarlos (`copy`), que es lo que se usó para volver a poner 23 PDF en Entrada. Consecuencia: quedan duplicados por nombre en Procesados (pendiente borrar los originales desde `farmando@`).

Fix: `Responder OK` arma su respuesta según si el ítem trae o no un campo `error`.

## Frontend (HTML estático en GitHub Pages)

- **Clave de acceso**: la página pide la clave una vez por sesión del navegador (`sessionStorage`, `holistor_token_v1`) y `fetchConTimeout` la manda en el encabezado `X-Holistor-Token` en todos los pedidos. La clave no está en el repositorio (es público) ni se comparte en el chat. Los `OPTIONS` (preflight) siguen funcionando porque n8n los responde antes de validar el encabezado.
- **Los cambios de la página los publica Claude Code desde la máquina del estudio** (esta sesión tiene el repositorio solo en lectura). Se entregan como parche `.patch` + `index.html` completo en el chat, y se confirma la publicación mirando la siguiente ejecución real de n8n (por ejemplo, que el body de `holistor-registro` traiga el campo nuevo).
- Lazy load de librerías pesadas (xlsx.js) solo cuando se necesitan — **con timeout explícito (15s)**, si no la promesa puede quedar esperando para siempre.
- Cache de API calls en sessionStorage con TTL.
- `media="print" onload="this.media='all'"` para CSS no bloqueante. `preconnect` a CDNs externos. `DocumentFragment` para múltiples inserts DOM.
- Polling de estado: intervalo 5s (`POLLING_INTERVAL_MS`, no escala con el tamaño del lote), timeout máximo proporcional a la cantidad de facturas vía `calcularTimeoutProceso()` — se recalcula sobre la marcha si el total real termina siendo mayor al esperado. El timeout debe pasar `prnReal = false` explícito al mostrar el estado final. Costo: 5 s fijos = ~130 ejecuciones de n8n por corrida de 11 min (pendiente sondeo adaptativo, P-02).
- **`FETCH_TIMEOUT_MS` (90s) es por pedido individual.** `POLLING_TIMEOUT_MS` (15 min) es código muerto, nunca usado.
- **Tandas de 40 archivos (`BATCH_FRONTEND_SIZE`)**: la página parte el envío en corridas encadenadas de 40, porque una sola ejecución de n8n aguanta ~80 facturas antes del `executionTimeout` de 2400 s. Hasta el 16/09 la constante solo se usaba para un cartel y nunca partía nada.
- **La espera de indexación de Drive antes de arrancar a procesar (`DRIVE_INDEX_DELAY_MS`, base 6s) escala con la cantidad de archivos subidos**: `calcularEsperaIndexacion(cantidadArchivos)` — base 6s, +400ms por archivo arriba de 5, techo de 20s. Aplicado en el flujo automático y en "Reintentar fallidas"; el botón manual (sin poder calcular la cantidad real) queda con la base fija.
- **Candado por proceso en curso**: el bloqueo de "Subir y procesar" para el mismo cliente/período aplica solo mientras hay un proceso en vuelo (`inFlight`); un PRN ya terminado no impide una corrida nueva del mismo mes (el backend protege contra duplicados por huella y clave). `request_id` se genera nuevo en cada corrida. El cartel de éxito muestra `verificacion.resumen.en_prn` (facturas en el archivo), no la cantidad de conciliadas. Los avisos de error quedan hasta que el usuario los cierra.
- **Una misma respuesta leída por dos partes del código sin orden garantizado.** El interceptor de `fetch` de `/holistor-estado` (abre el candado anti-doble-orden con `res.clone().json().then(...)`) y `iniciarPolling` (decide qué hacer con `await res.json()`) leen la misma respuesta cada uno por su lado. El 18/09 (SUC. DE CASTELLANO, 65 PDF) la parte que decide corrió primero y mandó la orden real con el candado todavía cerrado: "Bloqueado por frontend", 0 procesadas, dos veces seguidas. Regla: el estado que una decisión necesita se cambia **en el mismo lugar donde se toma la decisión**, no en otro lector paralelo de la misma respuesta. Fix 18/09: `iniciarPolling` abre el candado explícitamente en la rama `solo_escaneo` (parche entregado, pendiente de publicar y de corrida real).
- **Un camino que se saltea con `forzar` puede tapar un bug del camino normal.** "Sí, reprocesar" manda `forzar: true`, que saltea el candado; el camino "todo nuevo → procesar directo" (sin `forzar`) quedó sin probar después del cambio del candado del 16/09 y falló recién el 18/09. Al tocar el candado, probar los dos caminos.
- **Cuando una orden a n8n no pudo salir, la cadena de tandas tiene que cortarse**, no seguir con la siguiente tanda como si la anterior hubiera terminado (fix 18/09: `_corridaTerminada(false)` → `startUpload` corta con aviso). El caso "se venció el tiempo de espera" sigue continuando con la tanda siguiente (sin cambiar).
- **El reloj de la PC del estudio está ~76 s atrasado respecto de n8n** (medido el 18/09 comparando `request_id` con la hora de inicio de la ejecución). Al cruzar el registro de la página con las ejecuciones de n8n, sumar ese desfase.
- **Con la pestaña en segundo plano, Chrome baja el sondeo de estado a una consulta por minuto** (visto el 18/09: consultas cada 5 s mientras la pestaña estaba visible, una por minuto cuando no). No es un error, pero la página se entera del final de una corrida hasta un minuto tarde.
- No usar `onclick` en atributo HTML para zonas de upload — usar `addEventListener('click')`.
- `resetProcesoUX()` NO debe llamar a `updateProcesoUX()` — limpiar el DOM directamente.
- **Cuidado con referencias a variables no declaradas en ramas de código poco frecuentes**: un error de sintaxis ahí no se detecta hasta que ese camino específico se ejecuta, y puede colgar la página sin ningún aviso.
- **Un "listo" o resultado en pantalla puede corresponder a una corrida vieja/cacheada, no a la actual**: sospechar primero de un proceso zombie antes de asumir un bug de datos — usar "Liberar proceso" y revisar en vivo (Drive/Sheets).
- **Subida de PDFs — reintento automático incorporado**: `subirUnPDF()` hace hasta 4 intentos con espera creciente de 5 / 15 / 40 s entre uno y otro (desde el 22/09/2026; antes 3 intentos con 2.500 ms, que entraban en unos 6 s y no alcanzaban para un rechazo de Drive de 18 s), pensado para picos transitorios de 403/timeout. Además, `Upload PDF a Drive` reintenta del lado de n8n (5 intentos, 5 s). Con el fix de `Responder OK`, este reintento detecta correctamente los 403 que antes quedaban enmascarados.
- **ARCA tiene más de una descarga de comprobantes recibidos y no son intercambiables (22/09/2026).** "Mis Comprobantes Recibidos" trae título en la fila 1, títulos de columna en la fila 2, datos desde la 3, tipo como `1 - Factura A` y fechas `01/08/2026`. La otra (archivo `comprobantes_consulta_csv_recibidos_.xlsx`, con tildes rotas en los títulos) trae títulos en la fila 1, tipo `1`, fechas `8/1/26` y Cód. Autorización como `8.63E+13`. La página leía siempre desde la fila 3 sin mirar los títulos: con la otra descarga perdía el primer comprobante, guardaba fechas mes/día/año corto y el control de período no se hacía (la detección de período solo reconoce año de 4 dígitos). Desde el 22/09 `validarEstructuraExcelARCA` y el chequeo de fechas lo rechazan con aviso. El total con formato `$ 537,906.14` es normal en ambas descargas. Sospecha descartada con evidencia: la carga de este Excel NO causó las caídas del 22/09 (terminó bien 11 s antes de la primera; en la segunda no hubo carga).
- **Resumen honesto de subida parcial**: si algunos archivos fallan genuinamente (después de agotar los reintentos) mientras otros se suben bien, la página avisa explícitamente cuántos y cuáles.
- **Un mismo archivo PDF, guardado o descargado dos veces por el usuario, puede terminar con dos nombres completamente distintos** (ej. `img_t260901145313_n1.pdf` y `27226477409_011_00003_00000227 (2).pdf`). Un chequeo de duplicados por nombre de archivo nunca detecta este caso.
- **Excel de ARCA: leer los importes con `raw:true` (valor numérico real de la celda), no con el texto formateado.** El mismo problema que ya se había visto con `tipo_cambio` (el formato de visualización le saca el punto decimal) aplica a cualquier columna de importes; `parsearRegistroARCA` lee `rowsRaw` para el desglose (columnas 13-29, redondeadas a centavos) y manda `desglose_arca` en cada registro.
- **El botón "Procesar ahora" (`#btnProcesar`) está oculto (`display:none`) y nada lo muestra**; sin al menos un PDF en la cola no se puede disparar una corrida desde la página. Para disparar sin PDFs locales, llamar `Webhook Procesar` desde n8n (`execute_workflow`, body `{mes, anio, cliente_cuit, tiene_registro, forzar, soloEscanear}`) — `tiene_registro` no necesita el Excel: el registro se lee de la hoja. Desde el 09/10 el modo estricto no depende de este flag solo: `Indexar Registro` lo prende por su cuenta si el registro guardado de ese cliente/período tiene filas (ver "Modo estricto" más abajo), así que el flag ya no es lo único que lo prende (no se probó mandarlo en `false` con registro guardado).
- **`setNodeParameter` vs mandar un placeholder por error a un nodo real**: si en algún momento se necesita confirmar cómo se comporta una operación de edición antes de aplicar el cambio final, nunca hacerlo mandando texto de relleno a un nodo real en uso — verificar de otra forma. Error cometido dos veces en una misma sesión; el segundo error no tiene la excusa de no conocer el problema.
- **Complemento del 05/10/2026 a "Una misma respuesta leída por dos partes del código" (arriba)**: además del fix del 18/09 en `iniciarPolling`, el interceptor de `fetch` publicado (bloque `v19`) ya espera la lectura de la respuesta antes de devolverla: `const data = await res.clone().json()` dentro de un `try` (verificado en `index.html` e `index-test.html`). Así el estado del candado local queda fijado antes de que cualquier otro código reaccione a esa respuesta.
- **Un rechazo del servidor por proceso en curso (`proceso_ya_activo`) se muestra con el mensaje del servidor, nunca con el cartel genérico "n8n no respondió… usá Liberar proceso".** Ese consejo es peligroso acá: "Liberar proceso" soltaría el candado de la corrida que otra persona tiene en marcha. La página guarda el motivo del rechazo (`_ultimoRechazoProceso`) y `startUpload` lo muestra. Probado en TEST el 01/10 con dos navegadores: el candado frenó la segunda corrida, pero la pantalla mostró el cartel genérico; se corrigió.
- **Consultar el candado antes de subir, no después**: sin eso, el segundo usuario subía los 11 PDF a Drive y recién entonces recibía el rechazo (archivos duplicados en Entrada). `consultarCandado()` falla hacia el lado de seguir: si no puede consultar, devuelve `null` y el servidor sigue siendo la última barrera.
- **El presupuesto de tiempo se calcula una vez y alcanza para todo**: subida + registro + escaneo + procesamiento real. Cuando la parte previa consume una parte grande, a la corrida real le queda poco y la pantalla pasa a "Demorado" aunque todo ande bien. `SEG_POR_FACTURA` está en 40 s (la lectura completa real promedia ~25 s por factura: no dejar el presupuesto igual al promedio) y el presupuesto de la corrida real se reinicia al arrancar. "Demorado" no significa que el servidor haya fallado: mirar la ejecución en n8n antes de reintentar.
- **Clave de acceso vencida a mitad de una corrida**: `fetchConTimeout()` muestra un único cartel y marca `_claveRechazada`; `startUpload` y `sendFlush` cortan en vez de seguir subiendo PDFs que van a fallar todos por el mismo motivo (fix del 02/10/2026, en `index.html` e `index-test.html`).

- **Modo estricto "no figura en ARCA" (09/10/2026)**: antes solo se aplicaba si el Excel de ARCA se subía en esa misma sesión; sin Excel, una factura que no figuraba en el registro guardado entraba igual al PRN. Ahora `Indexar Registro` pone `tiene_registro = true` si el registro guardado tiene filas, y `Generar PRN` exige `tiene_registro === true` y registro con entradas. Resultado: la factura no registrada queda como `no_en_arca` (error; el PDF queda en Entrada) o `otro_cliente` (omitida) si el receptor parece de otro cliente. Las filas de `REGISTRO_ESPERADO` solo se crean al cargar el Excel, así que una factura sin registro nunca queda "procesada" ni dispara el cartel de reproceso. Verificado en producción con dos clientes (Actis Beatriz y Suc. de Castellano).

## Diseño completo — detección de duplicados en dos etapas (Etapas 1 y 2)

### Etapa 1 — lectura liviana + chequeo temprano de clave (por factura, dentro del Bucle)

Antes de gastar la lectura completa de Gemini (~8-11k tokens), cada factura pasa por hasta dos filtros baratos:

1. **Huella (SHA-256 del archivo)**, ya existía: agarra archivos idénticos byte por byte, sin necesitar ningún dato leído del PDF.
2. **Lectura liviana + clave temprana**, nueva: si la huella no encontró nada, un nodo Gemini con prompt corto (`Analyze document Ligero`, modelo `flash-lite`, `maxOutputTokens: 200`) extrae solo CUIT/tipo/punto de venta/número — ~800 tokens contra los 8-11k de la lectura completa. Con esos 4 datos se arma la clave real (`Calcular Clave Temprana`) y se compara contra:
   - `registroMap` (corridas anteriores) — **`forzar` sí saltea esta comparación**, es para eso que existe.
   - `clavesVistasEnEsteRun` (mismo lote actual) — **`forzar` NUNCA debe saltear esta comparación.**

Si cualquiera de las dos coincide, la factura se corta ahí (`Marcar Ya Procesada por Clave Temprana`) sin llegar nunca a la lectura completa. Si no coincide ninguna, sigue a `Analyze document` (completo) — con el binario del PDF reenganchado explícitamente (`$('Download file').item.binary`), porque el nodo Gemini de la lectura liviana no lo conserva en su salida.

**Estado real medido (16/09)**: la lectura liviana acierta la clave en 1 de 23 facturas, así que hoy esta etapa casi no corta nada; la huella sí funciona (detectó las 23 copias de la corrida del 16/09).

**Por qué hacen falta las dos protecciones (huella Y clave) y no alcanza con una sola**: la huella agarra "mismo archivo subido dos veces", pero no agarra "misma factura real, exportada como dos archivos distintos con bytes diferentes" (caso real: Brusa Luis Alberto, subido una vez como `img_t260901145314_n1.pdf` y otra como `20139203950_011_00001_00000103.pdf` — mismo comprobante, contenido binario distinto). La clave temprana sí agarra ese caso, porque compara el número de comprobante real, no el archivo. Y la clave definitiva tras la lectura completa (`Generar PRN` + `Acumular PRN`) lo agarra siempre.

### Etapa 2 — modo escaneo (`soloEscanear: true`)

El webhook `holistor-procesar` acepta un flag `soloEscanear`. Cuando es `true`, además de las dos protecciones de arriba, una factura que **no** es duplicado tampoco llega a la lectura completa — se anota como "nueva" (`Marcar Como Nueva (Escaneo)`, campo `p.nuevas_en_escaneo`) y se corta ahí también. En este modo, ninguna factura del lote pasa nunca por `Analyze document` completo, y no se genera ningún PRN — el proceso termina con un resumen (`solo_escaneo: true`, `nuevas_en_escaneo`, `ya_procesadas`, `duplicados_en_lote`) disponible vía `holistor-estado`, igual que cualquier otra corrida (no hay una respuesta especial del webhook — sigue el mismo patrón de "responder rápido, consultar resultado por sondeo" que ya usaba el resto del sistema).

**Flujo aplicado en la página**: primero se llama con `soloEscanear: true` (sin gastar nada de lectura completa); según el resultado, si hay algo repetido se le pregunta al usuario si quiere reprocesarlo también o solo lo nuevo ("Sí, reprocesar" → `forzar: true`); recién ahí se dispara la corrida real (`soloEscanear: false`). Si no hay nada repetido, se procesa directo sin preguntar nada. "Procesar ahora" pasa por el mismo camino; "Reintentar fallidas" no escanea: llama directo a `sendFlush(true)` (forzar) sobre los archivos que fallaron. Dos detalles menores del escaneo siguen abiertos (emisor vacío en la lista de nuevas; una nueva escrita en FALLOS) — en ClickUp.
